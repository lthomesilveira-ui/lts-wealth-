# V442 strategic planning and loading

The immutable UI preserves V441's financial actuals, Flow calculator, dated Aeternum provision and existing installments. The budget is in **Despesas → Balanço mensal**, below the balance. It is absent from the Dashboard. Native month/year input events select the period without requiring blur.

The plan distinguishes scheduled commitments and installments, essential variables, discretionary purchases and seasonal expenses. Regular net salary expected in each month supplies the income proposal; bonus and thirteenth salary do not increase it. Recorded spending and distinct remaining payments are combined, with recorded card consumption subtracted from the installment overlap. Existing owner-approved goals remain approved and unchanged. Past months without approved plans remain unknown instead of acquiring retrospective budgets.

Essential proposals retain a rounded recent reference until reviewed. Loan and financing proposals use identified remaining obligations instead of repeating paid history. Other recurring costs retain a conservative reference when no exact calendar entry is available. New discretionary spending uses only the remainder after essential costs and obligations, limited per category to half the recent reference and five percent of recurring income. A deficit remains visible when these constraints cannot fit the income; no contractual payment is scaled down. Seasonal obligations stay in the available calendar, with missing calendar details requiring review. These are proposals rather than owner acceptance or proof that all necessities have been identified.

Category details reuse the existing canonical expense-detail API and retain signed credits. Actual purchases, invoice payments, payroll withholdings and the Flow's provision are never added together as new spending. Approval uses the existing revision-guarded planning writer; deployment seeds no owner goals. The income editor can show validated source composition without changing its amount or creating extra events.

`strategic_reporting_install.sql` contains three guarded read/report changes: loan taxonomy, additional card/approval/thirteenth metadata from the existing budget builder, and optional income composition from the existing event editor. It preserves function attributes and rejects changed predecessors. Its installation must be checked separately from UI publication.

`install.sql` and `cash_install.sql` reuse results only within the same statement and input snapshot. Existing engines, cutoffs, source guards, grants, rights and timeouts are retained. `audit_install.sql` separately prepares the complete v6 calendar audit in the existing asynchronous worker. The public RPC requires owner authorization and reuses a result only for the exact date/horizon and matching sources, raw policy/reference/review inputs, ready version, implementation and digest. It never substitutes v4 or a successful empty result. Browser SQL limits are unchanged.

The separate audit migration was reapplied through the migration tool after its earlier confirmation expired. The existing worker completed a new guarded refresh, and an authenticated native read returned the full original audit within the unchanged request limit. Private evidence records its source version, exact-result parity and timing. These checks do not substitute for published UI verification.

Payroll, historical cash and corrected-cash readers also retain statement-local results without reserializing every hit or discarding intervening exact-range entries. Their original financial engines, ordered rows, source guards, privileges and optional-cache behavior remain protected. The planning reader exposes only unambiguous bindings from the owner's existing category dictionary; future installment labels reuse the established actual category before comparing commitments with recorded card consumption. A known mortgage spelling is aligned only for planning. Neither change rewrites source categories or amounts.

`payment_order_install.sql` separately corrects a received-invoice regression: reordering an otherwise identical issuer-payment array invalidated an existing reviewed settlement, allowing its checking debit to reappear as consumption. For the existing reviewed full-payment policy, both received and reviewed payment arrays are compared as exact collections of complete objects. Every identity, amount, date, currency, mode, type, non-payment invoice field, bank source, consumption manifest and coverage guard remains protected. Added, missing, duplicated or altered payments remain rejected. No original invoice, payment, confirmation or classification is rewritten; only the derived-cache epoch advances when implementation changes.

Synthetic checks retain all original budget writer/isolation/authorization and historical V441 financial assertions. Current-entry Chromium/WebKit cases cover mobile/desktop placement, year/month changes, a visible strategic deficit, category details, save/read races, approval preservation, failure states and unchanged Flow responses. They do not certify private-session or physical-iPhone acceptance. Private statements, balances and screenshots must stay outside this repository.

The reporting taxonomy also normalizes uppercase accented routing labels, known person prefixes, travel singular/plural and financing variants. Marketplace names alone never imply food. Source labels, person dimensions, amounts and dates are preserved. Its installer accepts the original or previously installed loan-only predecessor, preserves function attributes, rejects unknown concurrent changes, and advances the derived-cache epoch exactly once. The broader routing checks and both predecessor/idempotence/rejection paths run in reporting_test.mjs. These synthetic tests do not certify production installation or authenticated UI.
